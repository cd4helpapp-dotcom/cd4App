# CD4 Backend

The Java backend for CD4. It is meant to replace Supabase later. **It is not connected to the CD4 app, and it does not touch Supabase.**

## Stack

- Java 21, Spring Boot 3.4, Spring Security, Spring Data JPA, STOMP over WebSocket
- PostgreSQL 16 with pgvector
- Prisma 6 for the schema and migrations
- JWT access tokens (15 minutes) and rotating refresh tokens (30 days)
- Docker Compose and nginx

### How Prisma and Java fit together

Prisma has no Java client, so each tool does one job:

- **Prisma owns the database structure**: `prisma/schema.prisma` and `prisma/migrations/`.
- **JPA and JdbcTemplate run the queries.** Hibernate never changes the schema. It only checks that it matches.

## Running it

You need Docker Desktop for the database. To run the API outside Docker you also need JDK 21, which is not installed on this machine yet.

**Everything in Docker:**

```bash
cd backend
cp .env.example .env     # then set POSTGRES_PASSWORD and JWT_SECRET
docker compose up --build
```

| Address | What |
|---|---|
| `http://localhost/` | API through nginx |
| `http://localhost:8080/docs` | Swagger API docs |
| `http://localhost:8080/actuator/health` | Health check |
| `localhost:5433` | PostgreSQL (this machine only) |

**Database in Docker, API on your machine:**

```bash
docker compose up -d postgres migrate
mvn spring-boot:run
```

The API reads its settings from environment variables, so set the values from `.env` in your shell first. `DATABASE_URL` must then be the JDBC form: `jdbc:postgresql://localhost:5433/cd4`, along with `DATABASE_USERNAME` and `DATABASE_PASSWORD`. The `postgresql://` form in `.env` is only for Prisma.

## Settings

| Variable | Needed | Purpose |
|---|---|---|
| `POSTGRES_PASSWORD` | Yes | Database password |
| `JWT_SECRET` | Yes | Signs tokens, at least 32 random bytes. The app does not start without it |
| `CORS_ALLOWED_ORIGINS` | Yes | Allowed origins, comma separated. Also applies to the websocket |
| `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` | For payments | See the warning below |
| `AGORA_APP_ID`, `AGORA_APP_CERTIFICATE` | For calls | Without them, token requests return 503 |
| `OPENAI_API_KEY` | For AI | Without it, AI chat returns 503 and report reading ends as failed |
| `AI_CHAT_MODEL`, `AI_QUALITY_MODEL` | No | Chat and report reading models |
| `PRO_MONTHLY_PRICE_INR`, `PRO_YEARLY_PRICE_INR` | No | Default to 99 and 999 |
| `STORAGE_DIR` | No | Where uploaded files are kept |
| `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD` | Once | Creates the first admin, see below |

> **Warning: payments without Razorpay keys run in test mode.** Orders are marked as test orders and a booking succeeds with no money taken. Production must have the keys set.

### First admin

Set `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` (at least 12 characters) and start the app once. It only creates the account if no admin exists. Remove both values afterwards. Other admin and hospital accounts are created through `POST /api/v1/admin/accounts`. Public sign-up can only create patients and doctors.

## Changing the database

1. Edit `prisma/schema.prisma`.
2. Update the matching Java model.
3. Create the migration **without applying it**:

   ```bash
   cd prisma
   npx prisma migrate dev --create-only --name your_change
   ```

4. **Read the generated SQL before applying it.** The hand-written migration adds foreign keys, CHECK rules and partial unique indexes that Prisma's schema does not know about, so Prisma may propose dropping them. Delete those lines.
5. Apply it with `npx prisma migrate deploy`.

## Rules carried over from the current app

**Booking and payment**

- A slot must belong to the doctor, be free and be in the future. Times are Asia/Kolkata.
- One booking per patient and doctor every 30 days.
- A slot is held for 5 minutes for the patient who started paying.
- Fee comes from the doctor's profile, falling back to ₹500. The doctor's share is 70%.
- The payment signature is checked in constant time. A webhook without a valid signature is rejected.
- The app's verify call and the webhook can arrive together. Payment and slot rows are locked, so only one booking is created.
- If someone else got the slot first, the payment is refunded automatically. A failed refund is marked `needs_manual_refund`.
- Calls to Razorpay happen outside database transactions, so a slow payment API holds no locks.

**Cancel and reschedule**

- Patients can cancel or move up to 2 hours before the visit. Doctors and admins can cancel until it starts.
- A slot freed by a patient reopens. A slot cancelled by the doctor stays closed.
- Cancelling refunds any paid amount and notifies the other person.

**Chat and calls**

- Chat is open while a visit is ahead and for 30 days after the last one. Closed chats stay readable.
- A person can only read and subscribe to their own rooms. Sending over the websocket is blocked, so every message goes through the checked REST route.
- For an encrypted message, the server stores only the encrypted payload. Push notifications never contain message text.
- Only one live call per room, enforced by a database index even if both people dial together.
- Calls unanswered after 45 seconds become missed, and calls active for over 3 hours are closed.

**Security**

- Passwords use BCrypt. After 5 failed logins the account locks for 15 minutes.
- Unknown emails take as long to answer as wrong passwords.
- Refresh tokens are stored hashed and work once. Reusing an old one revokes that whole login family.
- Changing a password signs out other devices.
- Uploaded file types are decided from the file's own bytes, not the name the client sends.
- No file has a public link. Each download checks access.
- Public doctor data leaves out registration number, signature, KYC documents and contact details.
- New doctors are hidden from patients until an admin verifies them.

**Reports**

Reading has three steps: read the page, explain what was read, then check the explanation against the page. If the check finds a wrong claim, the draft is corrected once and checked again. If the check still fails or cannot run, the report ends as failed and **the patient sees nothing unchecked**. A report stuck for 6 minutes is marked failed.

**Improvements over the current app**

- A Pro subscription order is now saved against the person and the plan, so a cheap monthly payment cannot be claimed as a yearly plan.
- An account with upcoming appointments cannot be deleted until they are cancelled.
- A post can only use images that its author uploaded.

## Live events

Connect a STOMP client to `/ws`, sending `Authorization: Bearer <token>` in the CONNECT frame. Subscribe to `/topic/rooms/{roomId}`.

| Event | When |
|---|---|
| `message.new` | A new message |
| `message.read` | The other person read messages |
| `typing` | The other person is typing |
| `call.ringing` | A call started |
| `call.updated` | A call was answered, declined or ended |

Every response has this shape: `{ "success", "message", "code", "data" }`. Errors carry a `code` the app can act on, such as `slot_on_hold` or `booking_cooldown`.

## Not built yet

This backend does **not** yet do everything the Supabase version does.

**Needed before any real user**

- **Forgot password and email verification.** Neither exists, and they need an email provider.
- **Moving existing data from Supabase.** No migration script exists for users, files or history. Password hashes would also need a plan.
- **Connecting the app.** The app still talks only to Supabase.
- **Google and email OTP login.** The app uses both. This backend only has email and password.
- **Public hospital sign-up.** The website's form creates the hospital account and the request together. Here, an admin must create the account first.

**CD4 AI is a much smaller version**

The current agent is not ported. This version has the identity, medical-only scope, one-question-at-a-time history taking, a consult button and daily limits (20 free, 100 Pro). It does not have:

- WHO knowledge search (RAG). The tables exist but nothing uses them.
- Doctor and slot cards, or booking from inside the chat
- Streaming replies or the voice assistant
- Saved AI reports and the doctor brief

**Report reading is the core only**

The Supabase function is about 4,450 lines. This port has the reading prompt, the check and the fail-closed rule. It does not have the detailed parameter tables, lab range logic, model fallbacks, report search or the evaluation script. The `explain` prompt is new, so its quality has not been measured.

**Other missing features**

- Prescriptions: parsing, PDFs and sending them in chat
- Health reminders
- Hospital voice intake, adding patients to a hospital, doctor search and hospital profile editing
- Community ads, post shares and the list of who liked a post. The app uses `community_ads`, `community_ad_events` and `community_post_shares`, which are not in this schema yet.
- The medicine dictionary. `medicine_dictionary` and `hospital_voice_intake_sessions` are also missing from this schema.
- Most of the admin screens beyond doctor verification, reports, tickets, hospital requests and payouts
- Image safety scanning for Community posts
- Security monitoring and alerts
- Pro subscription payments through the webhook. Only the app's verify call activates a plan, so a closed app can leave someone paid but not upgraded.

## Known limits

- **One server only.** Chat events and rate limits live in memory. Running two copies needs Redis or similar.
- **Files are on local disk and not encrypted.** Docker keeps them in a volume, but nothing backs that volume up. Medical files should move to private object storage before launch.
- **No automatic database backups** are set up.
- **Agora tokens are unverified.** The builder follows Agora's format from memory and has not been tried on a real call.
- **Deleting an account also deletes its payment records** through the database links. Whether financial records must be kept is a legal question to settle before launch. A doctor with recorded payouts cannot be deleted, and the API answers with a conflict.
- **A hospital can add any doctor** without that doctor agreeing. This should be reviewed.
- **Feed paging uses page numbers**, so a new post can make an item repeat between pages.
